# AI Trip Planner RAG PRD

## 1. 产品概述

AI Trip Planner RAG 是一个面向旅行灵感探索与初步行程规划的 AI 助手 MVP。用户输入目的地、天数、预算、同行类型和偏好后，系统基于本地旅行知识库与结构化 mock data，生成多套可比较的行程方案，并给出预算拆分、住宿档位、交通建议、推荐理由和风险提示。

当前项目定位为 AI 产品经理作品集中的 MVP demo：重点展示从用户需求、AI 能力拆解、结构化规划、预算约束、排序评估到评测闭环的完整产品思路，而不是交付真实交易型旅行产品。

## 2. 阶段声明

当前阶段：MVP mock data。

本项目不使用真实用户数据，不连接真实酒店库存、机票/火车票库存、门票库存、支付系统、实时地图、实时交通或官方价格接口。所有预算、POI、酒店、交通与推荐内容均为产品演示和本地开发使用的估算或 mock 数据。用户面向真实出行前，仍需核对官方营业时间、票价、预约规则、交通状态和安全信息。

## 3. 背景与机会

旅行规划是高信息密度、强约束、多偏好的决策任务。传统搜索需要用户在景点、攻略、地图、酒店和预算表之间反复切换；通用大模型虽然能生成文本，但容易出现预算不可控、行程过载、字段不结构化、偏好响应不稳定等问题。

本 MVP 选择从“初步行程方案生成”切入，将 RAG 内容补充与确定性规划器结合：RAG 用于补充解释和推荐理由，预算估算、候选方案生成、排序与校验尽量保持结构化和可评测。

## 4. 目标用户与场景

以下为合成用户场景，用于产品定义和评测覆盖，不代表真实用户数据。

| 场景 | 用户任务 | 关键约束 | 成功体验 |
| --- | --- | --- | --- |
| 独行探索 | 想快速获得 1-3 天城市初游路线 | 预算有限、偏好明确 | 方案不超预算，覆盖核心兴趣点 |
| 情侣/朋友出游 | 需要兼顾体验感、餐饮和路线顺畅 | 兴趣多样、预算中等 | 多套方案可比较，有体验优先选项 |
| 亲子/长辈出游 | 需要低负载、休息充分、少折腾 | 每日 POI 不宜过多 | 行程节奏稳，风险提示清楚 |
| 商务间隙 | 只有半天到 2 天轻量探索 | 时间短、交通便利 | 推荐紧凑但不过载，可快速决策 |

## 5. 用户问题

1. 信息分散：用户需要跨攻略、地图、酒店、交通和预算工具拼装计划。
2. 预算不透明：生成式行程常给出“好玩”的路线，但缺少总预算和拆分。
3. 偏好响应不稳定：用户说“亲子”“慢游”“美食”，方案未必真正调整节奏和内容。
4. 行程负载过高：每天景点数量过多，忽略同行人群差异。
5. 输出不可评测：纯文本方案难以自动检查字段完整性、预算和偏好匹配。

## 6. 产品目标

### MVP 目标

- 让用户在一次输入后获得 3 套结构化、可比较的旅行方案。
- 每套方案必须包含每日 POI、住宿建议、交通建议、预算拆分、评分和 warning。
- 方案生成要显式考虑预算、天数、偏好和同行类型。
- 建立离线评测体系，持续检查 budget_fit、preference_match、plan_completeness、daily_load、warning_count。

### 非目标

- 不做真实预订、支付、库存确认或票务交易。
- 不承诺实时价格、实时营业状态、实时交通和安全事件。
- 不采集、存储或分析真实用户个人数据。
- 不把 mock 酒店、mock POI 或估算价格包装成真实可购买服务。

## 7. 成功指标

| 指标 | 定义 | MVP 目标 |
| --- | --- | --- |
| budget_fit | 选中方案总预算是否在用户预算内 | 核心场景通过率 >= 85% |
| preference_match | 方案内容是否覆盖用户显式偏好 | 平均分 >= 0.75 |
| plan_completeness | 输出字段、天数、POI、预算拆分是否完整 | 平均分 >= 0.95 |
| daily_load | 每日 POI 数量和时长是否符合同行类型 | 平均分 >= 0.85 |
| warning_count | 校验器产生的 warning 数量 | 核心 case 平均 <= 1 |

## 8. MVP 功能范围

### P0 功能

| 功能 | 说明 | 验收标准 |
| --- | --- | --- |
| 旅行输入表单 | 目的地、天数、预算、偏好、同行类型 | 必填/边界校验清晰 |
| RAG 知识检索 | 从本地知识库检索目的地上下文 | 返回 context 和 source |
| 多候选方案生成 | 经济型、舒适型、体验优先型 | 至少 3 个候选方案 |
| 预算估算 | POI、酒店、本地交通、餐饮、预留金 | 输出 total_budget 和 budget_breakdown |
| 排序评分 | 综合预算、偏好、强度和多样性 | 每个候选有 score 和 rank |
| 行程校验 | 检查字段、预算、天数、每日 POI 上限 | 输出 warnings 和 is_valid |
| 离线评测 | 使用合成 test cases 批量检查质量 | 生成 summary 和 case diagnostics |

### P1 功能

- 更细粒度的 POI 聚类与路线顺序优化。
- 用户可编辑某一天并重新生成局部行程。
- 增加“慢游、经典、亲子、深度体验”等模式切换。
- 支持导出 Markdown、PDF 或日历格式。

### P2 功能

- 接入真实地图、营业时间、票价、酒店和交通服务。
- 引入用户反馈闭环和在线 A/B 实验。
- 支持多人协作规划和版本对比。

## 9. 核心用户流程

1. 用户输入目的地、天数、预算、偏好和同行类型。
2. 系统检索本地知识库，得到相关旅行提示。
3. 规划器按不同策略生成多套候选行程。
4. 预算估算器计算各项费用和总预算。
5. 排序器综合预算匹配、偏好匹配、行程强度和多样性排序。
6. 校验器检查字段完整性、天数、每日负载和 warning。
7. 用户查看推荐方案、预算拆分和风险提示。

## 10. AI 能力设计

| 能力 | 当前实现 | 产品取舍 |
| --- | --- | --- |
| RAG | 本地知识库 + FAISS 检索 | 用于补充推荐理由，不直接决定预算 |
| 规划 | 确定性候选生成器 | 便于评测和复现，降低幻觉风险 |
| 预算 | 本地规则估算 | 不依赖实时价格，明确为 mock estimate |
| 排序 | 多指标加权评分 | 让方案可比较，可解释 |
| 校验 | 规则化 validator | 提前发现预算、字段和负载问题 |

## 11. 数据策略

- 数据来源：本地知识库、结构化 mock POI、mock 酒店、mock 交通规则。
- 数据边界：仅用于演示、开发和评测，不代表真实世界价格或库存。
- 隐私策略：当前不采集真实用户数据；评测集只包含合成场景。
- 质量策略：每次修改 planner、ranker、budget_estimator 或 validator 后，运行离线评测，观察核心指标变化。

## 12. 用户体验原则

- 结构优先：预算、天数、每日安排、理由和 warning 必须可扫描。
- 明确边界：所有估算和 mock 数据都应被标注为建议，不包装成确定信息。
- 允许比较：不要只给一个答案，至少提供不同预算/体验策略的候选。
- 低负载友好：亲子、长辈、商务场景默认减少每日 POI 数量。
- 可解释：推荐理由应说明与偏好、RAG 信息或策略的关系。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 预算估算不准 | 用户误判成本 | 明确 mock estimate，未来接实时价格源 |
| 行程过载 | 体验变差 | daily_load 指标和 validator 共同约束 |
| 偏好只被复述 | 方案质量虚高 | 评测优先检查 POI category/tags/theme |
| RAG 内容过期 | 推荐不可靠 | 标注需要用户核对官方信息 |
| 输出字段漂移 | 前端/API 难以消费 | plan_completeness 作为发布门槛 |

## 14. 路线图

| 阶段 | 目标 | 关键交付 |
| --- | --- | --- |
| MVP mock data | 证明结构化 AI 规划闭环 | 多候选方案、预算、排序、校验、评测 |
| Alpha | 提升真实可用性 | POI 聚类、路线顺序、编辑再生成、导出 |
| Beta | 接入真实服务 | 地图、营业时间、价格、库存、用户反馈 |
| GA | 交易与协作 | 预订跳转、多人协作、账户与历史计划 |

## 15. 开放问题

- 预算应按“每人”还是“总团费”作为默认输入口径？
- RAG 内容是否需要按城市建立结构化 source confidence？
- 对亲子、长辈和商务场景，是否需要单独的安全和便利性指标？
- 当预算与偏好冲突时，产品应优先保预算、保偏好，还是显式给出取舍方案？
